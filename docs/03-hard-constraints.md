## Hard constraints — the walls

### A. Apple approval and account gates

1. **A paid Apple Developer Program membership ($99/yr) is mandatory, even for a build only you will ever run.** Apple's *Supported capabilities (iOS)* table checks **Family Controls (development)** in the **ADP column only** — the ADEP and free "Apple Developer" (Personal Team) cells are empty. Apple DTS, verbatim: *"The Apple Developer column shows all the capabilities available to folks using free provisioning, aka a Personal Team. There's no supported way to use capabilities that aren't listed there."* Xcode will not offer the capability on a Personal Team. **The 7-day free-provisioning cert expiry never becomes the binding constraint — the capability is simply unobtainable.**
2. **Apple Developer Enterprise Program is also unchecked.** You cannot ship a Family Controls app via in-house enterprise distribution.
3. **The distribution entitlement is a managed capability requiring manual human review**, requested by the **Apple Developer Account Holder specifically** (not an Admin, not a developer) at `https://developer.apple.com/contact/request/family-controls-distribution`, or via the *Capability Requests* tab in Certificates, Identifiers & Profiles.
4. **A separate request per App ID, including every extension.** Apple, verbatim: *"If your app includes a Screen Time API app extension such as Device Activity Monitor, Device Activity Report, Shield Action, or Shield Configuration, submit the same request for the extension."* For this architecture that is **5 requests**. Success state: the capability reads **"Assigned"** and the info button's *Provisioning Support* lists every distribution method you need.
5. **Bundle-ID casing is load-bearing across parent/extension.** Real failure (thread 819573): parent approved as `com.hayashikento.FocusPact`, extension requested as `com.hayashikento.focuspact.ShieldConfigurationExtension` → Xcode "Prefix Mismatch" error, archiving blocked, re-request required. **Lock casing before filing anything.**
6. **TestFlight — internal AND external — requires the distribution entitlement.** Apple DTS, verbatim Q&A: *"Can I distribute a build for internal testers via TestFlight without waiting for Apple's reply to my request?" — "No."* The only pre-approval multi-device path is **development signing with each tester's UDID registered on the development provisioning profile** (100 devices/year per device class).
7. **No SLA, no ticket ID, no confirmation email.** The form returns only "Thank you for requesting the API." Observed 2026 range: 1 day to 6+ weeks. Approval email can land while the portal still reads "Submitted," hard-blocking App Store Connect submission with no self-service remedy (thread 820971). The Developer Support contact form itself has been reported broken.
8. **`com.apple.developer.family-controls.app-and-website-usage` is a second, separately-requested gated capability** (iOS 26.4+). Even with it, `.approvedWithDataAccess` is **never** returned outside the EU or for non-EU Apple Accounts. Only **one app per device** can hold it — if the user grants it elsewhere, your status **silently reverts to `.notDetermined`**. It also forces an **all-or-nothing consent prompt** (thread 820283) and reportedly **evicts Apple's own Screen Time from usage data** (thread 844661), which may break the parent's iOS 27 Time Allowances. And it is currently reported broken in distribution builds while working in development (threads 844541, 844623).

### B. Platform reach

9. **macOS is not available.** Apple Frameworks Engineer, verbatim: *"The Screen Time APIs are currently for iOS only."* Mac Catalyst is listed at 15.0 in the entitlement metadata but fails at runtime: `The connection to service named com.apple.FamilyControlsAgent was invalidated: failed at lookup with error 159 - Sandbox restriction.` Family Controls appears in **none** of Apple's macOS / visionOS / tvOS supported-capabilities tables. **Target iOS + iPadOS only.**
10. **Family Controls authorization always fails for an iPhone/iPad app running on visionOS** (documented by Apple). visionOS support is contradictory across Apple's own pages — treat as unsupported. *(unverified)*
11. **No Simulator support, ever.** `requestAuthorization` fails (commonly `FamilyControlsError` code 3, `.invalidArgument`); the picker, shields, monitor callbacks, and reports are all physical-device-only. **No amount of CI can test the real behavior.**
12. **An individual cannot enroll on a device with no passcode** — `FamilyControlsError.authenticationMethodUnavailable`. Enrollment also requires network (`.networkError`) and a valid iCloud account (`.invalidAccountType`).

### C. The enforcement ceiling (the ones that define the product)

13. **Under `.individual`, Apple deliberately removes the anti-bypass protections.** Verbatim: *"the system removes any restrictions that prevent the user from bypassing parental controls so the user can delete an authorized app or sign out of iCloud as needed."* An adult self-control app **cannot be made undeletable.**
14. **The user can revoke everything in ~4 taps** (Settings → Screen Time → Apps with Screen Time Access, or Settings → Apps → [your app]). Every `ManagedSettingsStore` restriction lifts instantly and all issued tokens are voided. **There is no API to block, delay, or reliably detect this.** `$authorizationStatus` does not emit on revoke while backgrounded without a debugger attached (thread 820796, open, no Apple response). **Settings.app cannot be shielded**, which structurally guarantees this hatch stays open.
15. **`denyAppRemoval` is device-wide, not per-app**, is only honored under `.child` enrollment (Apple staff, thread 729637), and has been reported to get stuck on after your app is uninstalled (thread 818905).
16. **`.child` authorization is exclusive** — a second app gets `FamilyControlsError.authorizationConflict`. `.individual` has no such limit.
17. *(unverified)* iOS 26.4 reportedly added Screen Time passcode gating on revoking a third-party app's access, with a Face ID bypass bug fixed only in the iOS 27 public beta (thread 821959, developer report, no Apple documentation; support.apple.com was unreachable for verification). **Do not ship marketing copy asserting this until you retest on the iOS 27 GM.**

### D. What the API structurally cannot do

18. **No "app was opened" or "app was closed" callback exists anywhere.** Apple DTS (thread 838231) also rules out `NSUserActivity`, Shortcuts intents, URL schemes, App Intents, and Live Activities as automatic triggers.
19. **No app can bring itself to the foreground.** Apple DTS, verbatim: *"iOS does not provide a supported API for an application to programmatically bring itself to the foreground, and Family Controls does not grant any exceptions for this purpose."* Only `ShieldActionResponse.openParentalControlsApp` (iOS 26.5+). Private-API workarounds (`-[LSApplicationWorkspace openSensitiveURL:withOptions:]`) — Apple Frameworks Engineer: *"Some apps may have figured out ways to call up private API that should be rejected in App Review."* A rejection on exactly this was reported May 2026.
20. **You cannot open the *blocked* app after a successful intervention.** You hold only an opaque token; `OpenAppFromApplicationTokenIntent` (FB15500695) got no Apple response. **The user must navigate back manually.**
21. **No app can draw above another app.** No `SYSTEM_ALERT_WINDOW` / `TYPE_APPLICATION_OVERLAY` analogue, no window level above the frontmost app.
22. **No synchronous pre-launch interception.** The token must already be in `store.shield.applications` *before* launch. Any "decide dynamically" logic must be pre-computed.
23. **No always-running background service.** Enforcement code runs only in the monitor extension on system-scheduled callbacks, under 6 MB, plus opportunistic `BGAppRefreshTask`/`BGProcessingTask`.
24. **You cannot suspend, freeze, force-quit, or deny background execution/notifications to another app.** Shielded apps keep running and keep receiving pushes.
25. **App identity is opaque.** No bundle IDs, no names, no icons (outside the EU / outside the ShieldConfiguration extension). You cannot enumerate installed apps, preset or server-sync a blocklist, recommend "block TikTok," or tell an accountability partner *which* apps are blocked.
26. **Web blocking is whole-domain only.** No per-URL or per-path blocking.
27. **`intervalDidStart` / `intervalDidEnd` fire only when the device is in use**, never at the wall-clock boundary.
28. **The shield is a fixed template.** No custom views, SwiftUI, animation, video, text input, or live countdown.
29. **Cross-process push signaling is not provided.** Apple Frameworks Engineer, verbatim: *"a NotificationCenter can only deliver notifications within a single program; it does not allow you to post a notification to other processes."* No KVO across the App Group boundary; `CFNotificationCenterGetDarwinNotifyCenter()` works but only reaches a *running* receiver, and extensions usually are not resident.

### E. Sandbox and resource walls

30. **The DeviceActivityReport extension sandbox is intentional and absolute** (Apple DTS: "Yes."). No usage number computed inside it can reach your app by any channel. **Outside the EU there is NO way to persist Screen Time totals into your own database.**
31. **6 MB hard memory ceiling on the DeviceActivityMonitor extension**, unchanged since iOS 15, not increasable (Apple staff: *"it seems to be the limit for now and there is no way to increase it"*). This eliminates SwiftData, Core Data stacks, analytics SDKs, networking clients, and image work from that process.
32. **The monitor extension is killed for memory OR idleness**, confirmed by an Apple Frameworks Engineer: *"Killed when using too much memory," "Killed when idle too long," "The service should restart the next time you request information."* It has also been reported as **never launched at all** on iOS 26.3.1 despite correct configuration (thread 819224; Apple DTS response was only "file a Feedback report"). **It cannot be your sole enforcement path.**
33. **`ShieldConfigurationDataSource` and `ShieldActionDelegate` are network-blocked** and latency-bounded (the system substitutes its default shield if you're slow). All shield content must be pre-staged in the App Group.
34. **The four hard numeric caps fail silently**: 50 tokens per shield collection, 50 named stores, 50 filter domains, 3 submenu items. Exceeding the token cap makes the store shield *nothing* and read back `nil`. **Guard `tokens.count <= 50` in your own code.**

### F. Reliability walls you must design around

35. **`eventDidReachThreshold` is the least reliable part of the API.** Documented failure modes across iOS 26.2–26.5.2: fires immediately on first unlock; fires with 0 recorded Screen Time minutes (reproducible by leaving a device idle/locked then plugging into power); fires twice for the same event; fires when the threshold was not met; or silently never arrives. Feedback IDs: FB21450954, FB21267341, FB21560904, FB18927456, FB18061981, FB14082790, FB15079668, FB16249607, FB17272792, FB22304617. Apple's only partial fix landed in 26.5 beta 1 and the reporter describes it as *"not consistently reproducible… just to come back and hit even harder the next time."* **Design for both false positives (fast unshield path) and false negatives (reconcile on every foreground).**
36. **`ApplicationToken`s go stale.** Tokens change after OS updates and re-authorization; tokens handed to `ShieldConfigurationDataSource` / `ShieldActionDelegate` can fail `==` against tokens you stored (thread 814571, iOS 26.2.1; Apple DTS asked for Feedback, gave no workaround). The iOS 26.5 remedy (`TokenExpiryMessage` + `refresh(_:)`) is **itself reported broken**: ~30% of new users receive `.tokensDidExpire` immediately after granting approval (FB23391495, thread 844148, Apple status "Potential fix identified — For a future OS update"). **Ship a token-reselection recovery flow as a first-class feature, not an error path.**
37. **Shields can persist after your app is deleted** with no UI to remove them (thread 802242). Always offer a prominent teardown.

### G. App Store policy

38. **Guideline 4.10** names "Screen Time APIs" among capabilities you may not monetize. Never label a paywalled tier "App Blocking" or "Screen Time"; never put `requestAuthorization` or `FamilyActivityPicker` behind the paywall.
39. **Guideline 2.5.1 is what actually gets these apps rejected.** Two verbatim rejections: *"your app uses ScreenTime API to hide apps"* (for `blockedApplications`, used exactly as documented; appeal denied with the same copy-pasted text), and *"the app still includes ScreenTime API without ScreenTime features… It would be appropriate to remove these APIs from the app if you have no approved use case."* 2.5.1 also requires you to **"indicate that integration in their app description"** — your App Store description must say you use Screen Time to block apps.
40. **Guideline 5.4** requires **organization** enrollment (not individual) for any `NEVPNManager` content-blocking layer, with removal from the App Store *and* possibly the Developer Program for non-compliance.
41. **Already in force as of September 2026:** you cannot submit a new app, a version update, or a notarization request without answering the **social-media capability questions in the App Store Connect age-rating questionnaire**. For an app blocker the answer is "No," which keeps you out of the Social Media Time Allowance bucket. There is no API to read, override, or appeal Time Allowance category assignment.
42. **Privacy manifests are required per-bundle** — the app and **each of the four `.appex` bundles** need their own `PrivacyInfo.xcprivacy`. Apple: *"For each executable or dynamic library in an app that uses a required reason API, the bundle that includes the executable or dynamic library needs to include a privacy manifest file that reports the API."* App Group `UserDefaults` requires reason code **`1C8F.1`**, not `CA92.1`.
43. **Privacy policy required in two places** — the App Store Connect metadata field *and* inside the app, reachable without an account (5.1.1(i)). If you support account creation you must offer in-app account deletion (5.1.1(v)).
